Πρόκειται για πολύ καλά δομημένο codebase. Τα layers είναι καθαρά, το MVI συμβόλαιο ανά feature είναι συνεπές, ο reducer του κεντρικού screen είναι πραγματικά pure και testable, και η κρυπτογράφηση των favorites είναι υλοποιημένη σωστά (AES-256/GCM, κλειδί στο AndroidKeyStore, versioned payload, authenticated encryption). Υψηλή H-1 Το safeApiCall καταπίνει το CancellationException

core/SafeCall.kt:20

Το πρόβλημα. Το τελευταίο catch (e: Exception) πιάνει και το CancellationException — στην Kotlin είναι java.util.concurrent.CancellationException, δηλαδή κανονικό Exception. Όταν ακυρωθεί το viewModelScope (ο χρήστης φεύγει από την οθόνη) ή όταν το loadFirstPage ακυρώνει το προηγούμενο job σε κάθε πάτημα πλήκτρου στην αναζήτηση, η ακύρωση δεν διαδίδεται: μετατρέπεται σε AppError.Unknown.

Γιατί έχει σημασία. Σπάει το structured concurrency. Πρακτικά: μια ακυρωμένη αναζήτηση γράφει Change.LoadFailed στο state, οπότε ο χρήστης βλέπει «Κάτι πήγε στραβά» ενώ απλώς πληκτρολόγησε το επόμενο γράμμα. Επιπλέον, η coroutine συνεχίζει να εκτελεί κώδικα μετά την ακύρωσή της.

// ΤΩΡΑ — το CancellationException είναι Exception, άρα πιάνεται εδώ
} catch (e: Exception) {
    Result.failure(AppErrorException(AppError.Unknown(e)))    // ← και η ακύρωση
}

// ΠΡΟΤΑΣΗ — η ακύρωση ξαναπετιέται πριν από οτιδήποτε άλλο
suspend fun <T> safeApiCall(block: suspend () -> T): Result<T> = try {
    Result.success(block())
} catch (e: CancellationException) {
    throw e                                                  // ← ποτέ δεν το καταπίνουμε
} catch (e: IOException) {
    Result.failure(AppErrorException(AppError.Network))
} catch (e: HttpException) {
    val error = if (e.code() == 401 || e.code() == 403) AppError.Unauthorized else AppError.Http(e.code())
    Result.failure(AppErrorException(error))
} catch (e: Exception) {
    Result.failure(AppErrorException(AppError.Unknown(e)))
}

Το ίδιο μοτίβο υπάρχει και στο EncryptedFavoritesSerializer.readFrom (βλ. M-7) και στο KeystoreCryptoManager.decrypt. Ως κανόνας: κάθε γενικό catch (e: Exception) μέσα σε suspend function χρειάζεται ένα catch (e: CancellationException) { throw e } από πάνω του.

Υψηλή H-2 Τέσσερα ανεπίβλεπτα viewModelScope.launch γύρω από writes → crash

ui/popular/PopularViewModel.kt:74 · ui/details/DetailsViewModel.kt:65 · ui/favorites/FavoritesViewModel.kt:46 · ui/profile/ProfileViewModel.kt:42

Το πρόβλημα. Και στα τέσσερα σημεία καλείται ένα suspend use case που γράφει στο DataStore, χωρίς try/catch και χωρίς CoroutineExceptionHandler:

is Intent.FavoriteToggled -> viewModelScope.launch {
    toggleFavorite(intent.movie)   // αν πετάξει, κανείς δεν το πιάνει
}

Γιατί έχει σημασία. Το viewModelScope είναι SupervisorJob + Dispatchers.Main.immediate χωρίς exception handler. Ένα SupervisorJob εμποδίζει τη διάδοση στα siblings, δεν καταπίνει το exception: αυτό φτάνει στον default uncaught exception handler και ρίχνει την εφαρμογή. Το DataStore.updateData πετάει IOException σε αποτυχία εγγραφής, και το KeystoreCryptoManager.encrypt μπορεί να πετάξει KeyStoreException ή CryptoUnavailableException αν το κλειδί ακυρωθεί ανάμεσα στο read και το write. Ένα πάτημα στο bookmark με γεμάτο δίσκο ή με ακυρωμένο κλειδί = crash.

Πρόταση. Το Intent.Refresh του FavoritesViewModel το κάνει ήδη σωστά (runCatching). Επεκτείνετέ το στα υπόλοιπα, με ορατό μήνυμα αντί για σιωπή:

is Intent.FavoriteToggled -> viewModelScope.launch {
    runCatching { toggleFavorite(intent.movie) }
        .onSuccess { isFavorite ->
            emit(Effect.ShowMessage(UiText.res(
                if (isFavorite) R.string.message_added_to_favorites
                else R.string.message_removed_from_favorites,
            )))
        }
        .onFailure { emit(Effect.ShowMessage(it.toAppError().toUiText())) }
}

Εναλλακτικά (πιο καθαρό για MVI): αλλάξτε το FavoritesRepository.toggle ώστε να επιστρέφει Result<Boolean>, οπότε η αποτυχία γίνεται τύπος αντί για exception — ακριβώς όπως ήδη κάνει το MovieRepository με το safeApiCall. Αυτό θα έκανε και τη συμπεριφορά των δύο repositories συνεπή μεταξύ τους.

Υψηλή H-3 Race condition (TOCTOU) στο FavoritesRepositoryImpl.toggle()

data/repository/FavoritesRepositoryImpl.kt:39-50

Το πρόβλημα. Το wasFavorite διαβάζεται σε ξεχωριστή συναλλαγή, πριν το updateData, και μετά χρησιμοποιείται μέσα του:

override suspend fun toggle(movie: Movie): Boolean = withContext(dispatchers.io) {
    val wasFavorite = dataStore.data.first().movies.any { it.id == movie.id }   // read #1
    dataStore.updateData { current ->                                          // write, με παλιά πληροφορία
        val without = current.movies.filterNot { it.id == movie.id }
        if (wasFavorite) current.copy(movies = without)
        else current.copy(movies = without + movie.toFavorite(System.currentTimeMillis()))
    }
    !wasFavorite
}

Γιατί έχει σημασία. Το DataStore σειριοποιεί τα updateData, αλλά δεν σειριοποιεί το ζεύγος read-then-write. Δύο γρήγορα πατήματα στο bookmark (ή ένα πάτημα στη λίστα ενώ είναι ανοιχτή η οθόνη λεπτομερειών) εκτελούν δύο toggle παράλληλα: και τα δύο διαβάζουν wasFavorite = false, και τα δύο προσθέτουν, και τα δύο επιστρέφουν true. Η ταινία μένει στα αγαπημένα ενώ ο χρήστης πάτησε άρτιο αριθμό φορών, και το μήνυμα που βλέπει είναι λάθος. Υπάρχει επίσης περιττό κόστος: δύο αναγνώσεις σημαίνουν δύο αποκρυπτογραφήσεις του αρχείου αντί για μία.

Πρόταση. Όλα μέσα στη μία ατομική συναλλαγή που ήδη προσφέρει το DataStore — το updateData επιστρέφει τη νέα τιμή:

override suspend fun toggle(movie: Movie): Boolean = withContext(dispatchers.io) {
    val updated = dataStore.updateData { current ->
        val without = current.movies.filterNot { it.id == movie.id }
        // η απόφαση παίρνεται πάνω στο current της ίδιας της συναλλαγής
        if (without.size != current.movies.size) current.copy(movies = without)
        else current.copy(movies = without + movie.toFavorite(System.currentTimeMillis()))
    }
    updated.movies.any { it.id == movie.id }
}

Υψηλή H-4 Η επαναφόρτωση μετά από αλλαγή γλώσσας δεν εκτελείται ποτέ

ui/popular/PopularScreen.kt:94-102 · AndroidManifest.xml:17-21

Το πρόβλημα. Ο κώδικας σκοπεύει να ξαναφορτώσει τη σελίδα 1 όταν αλλάξει η γλώσσα, παρακάμπτοντας την πρώτη σύνθεση ώστε να μη γίνει διπλό fetch στην εκκίνηση:

var isFirstLocale by remember { mutableStateOf(true) }   // ← remember, όχι rememberSaveable
LaunchedEffect(locale) {
    if (isFirstLocale) isFirstLocale = false
    else viewModel.onIntent(Intent.Retry)
}

Γιατί έχει σημασία. Η MainActivity δεν δηλώνει android:configChanges, άρα μια αλλαγή γλώσσας ξαναδημιουργεί το Activity. Η νέα σύνθεση ξεκινά με φρέσκο remember, οπότε το isFirstLocale είναι ξανά true: το effect απλώς το θέτει false και δεν καλεί ποτέ το Retry. Ταυτόχρονα το ViewModel επιβιώνει της ανακατασκευής, άρα κρατάει τη λίστα στην παλιά γλώσσα. Αποτέλεσμα: ο χρήστης αλλάζει σε Ελληνικά και οι τίτλοι/κατηγορίες παραμένουν στα Αγγλικά μέχρι το επόμενο χειροκίνητο refresh. Ο μηχανισμός που περιγράφει το σχόλιο δεν ενεργοποιείται σε καμία περίπτωση.

Πρόταση. Το ίδιο το FavoritesRoute λύνει το ίδιο πρόβλημα σωστά, με LaunchedEffect(Unit), ακριβώς επειδή αυτό ξανατρέχει σε κάθε νέα σύνθεση. Εδώ όμως χρειάζεται να ξεχωρίσει η ανακατασκευή λόγω γλώσσας από την πρώτη εκκίνηση, οπότε η κατάσταση πρέπει να επιβιώσει της ανακατασκευής:

val languageTag = LocalConfiguration.current.locales[0].toLanguageTag()
// rememberSaveable: επιβιώνει του Activity recreation μέσω savedInstanceState
var loadedForLanguage by rememberSaveable { mutableStateOf(languageTag) }
LaunchedEffect(languageTag) {
    if (loadedForLanguage != languageTag) {
        loadedForLanguage = languageTag
        viewModel.onIntent(Intent.Retry)
    }
}

Πιο σωστά ακόμη, η γλώσσα με την οποία φορτώθηκαν τα δεδομένα είναι ιδιότητα των δεδομένων, όχι του UI: αν το PopularViewModel κρατούσε το language tag της τελευταίας φόρτωσης, η οθόνη δεν θα χρειαζόταν καθόλου αυτή τη λογική. Βλ. και M-1, που είναι η δεύτερη μισή του ίδιου προβλήματος.

Μεσαία M-1 Το GenreCache δεν ακυρώνεται ποτέ σε αλλαγή γλώσσας

data/remote/GenreCache.kt:18-33

Το πρόβλημα. Το cache: Map<Int, String> γεμίζει μία φορά ανά process και δεν καθαρίζεται ποτέ. Το genre/movie/list όμως επιστρέφει μεταφρασμένα ονόματα, επειδή ο LanguageInterceptor προσθέτει το language σε κάθε request.

Γιατί έχει σημασία. Είναι ακριβώς το σενάριο που ο LanguageInterceptor γράφτηκε για να καλύψει — το σχόλιό του λέει ρητά ότι διαβάζει τη γλώσσα φρέσκια σε κάθε κλήση «γιατί μια τιμή σε @Singleton θα έχανε μια αλλαγή locale». Το GenreCache είναι ακριβώς μια τέτοια τιμή σε @Singleton. Αποτέλεσμα: ακόμη και αν διορθωθεί το H-4, οι κατηγορίες στη λίστα θα παραμείνουν στην παλιά γλώσσα μέχρι να σκοτωθεί το process.

Πρόταση. Κλειδώστε το cache πάνω στη γλώσσα:

@Singleton
class GenreCache @Inject constructor(
    private val api: TmdbApi,
    private val currentLanguage: () -> String = { languageForLocale(Locale.getDefault()) },
) {
    private val mutex = Mutex()
    private var cachedLanguage: String? = null
    private var cache: Map<Int, String>? = null

    private suspend fun genres(): Map<Int, String> {
        val language = currentLanguage()
        cache?.takeIf { cachedLanguage == language }?.let { return it }
        return mutex.withLock {
            cache?.takeIf { cachedLanguage == language } ?: runCatching {
                api.movieGenres().genres.associate { it.id to it.name }
            }.getOrDefault(emptyMap())
                .also { if (it.isNotEmpty()) { cache = it; cachedLanguage = language } }
        }
    }
}

Δευτερεύον σημείο: σε αποτυχία, το cache μένει άδειο και κάθε επόμενη σελίδα ξαναδοκιμάζει το δικτυακό call μέσα στο mutex, σειριοποιώντας όλα τα mappings πίσω από ένα timeout. Ένα μικρό negative-cache window (π.χ. μη ξαναδοκιμάσεις για 30 δευτερόλεπτα) το αποτρέπει.

Μεσαία M-2 Το UiText είναι unstable, άρα κανένα screen δεν κάνει skip

core/UiText.kt:12 · ui/details/DetailsContract.kt:8 · ui/profile/ProfileContract.kt:7

Το πρόβλημα. Το UiText.Res έχει πεδίο args: List<Any>. Μια σκέτη List θεωρείται unstable από τον Compose compiler, άρα unstable είναι και το UiText, άρα και κάθε State που το περιέχει.

Γιατί έχει σημασία. Το project έχει ήδη ενεργοποιημένα τα Compose compiler reports και έχει προσέξει τη σταθερότητα παντού αλλού — βάζει @Immutable στα domain models και στα PopularContract.State/FavoritesContract.State. Αυτό όμως το ακυρώνει: τα ErrorState(message: UiText), SnackbarMessage(message: UiText?) και τα DetailsContract.State / ProfileContract.State (που δεν έχουν καν @Immutable) δεν είναι skippable, οπότε ξανατρέχουν σε κάθε recomposition του γονέα ακόμη κι όταν τίποτα δεν έχει αλλάξει.

Πρόταση. Τρεις μονόγραμμες διορθώσεις:

// core/UiText.kt
@Immutable
sealed interface UiText {
    @Immutable data class Dynamic(val value: String) : UiText
    @Immutable data class Res(@StringRes val id: Int, val args: List<Any> = emptyList()) : UiText
}

// DetailsContract.kt και ProfileContract.kt — όπως ήδη κάνουν τα άλλα δύο contracts
@Immutable data class State(...)

Αν προτιμάτε να μην υπόσχεστε σταθερότητα με annotation, το ίδιο αποτέλεσμα δίνει το stabilityConfigurationFile του Compose compiler — και είναι επίσης η λύση για να φύγει το androidx.compose.runtime.Immutable από το domain/ (βλ. L-5). Επαληθεύστε το αποτέλεσμα στο build/compose_reports/*-classes.txt, που ήδη παράγεται.

Μεσαία M-4 Το pagination trigger μπορεί να ζητήσει την ίδια σελίδα δύο φορές

ui/popular/PopularScreen.kt:334-340 · ui/popular/PopularViewModel.kt:89-99

Το πρόβλημα. Δύο ζητήματα που αλληλοενισχύονται. Πρώτον, το LaunchedEffect ζει μέσα στο scope του τελευταίου item, οπότε η ύπαρξή του εξαρτάται από ένα if πάνω σε state που αλλάζει. Δεύτερον — και πιο σημαντικό — ο φρουρός στο ViewModel διαβάζει state που ενημερώνεται ασύγχρονα:

private fun loadNextPage() {
    val current = _state.value
    if (current.isLoading || current.isLoadingMore || current.endReached) return   // έλεγχος
    loadJob = viewModelScope.launch {
        update(Change.NextPageLoading)   // το isLoadingMore γίνεται true ΜΟΝΟ εδώ, μετά το dispatch
        load(page = current.page + 1, replace = false)
    }
}

Γιατί έχει σημασία. Ανάμεσα στον έλεγχο και στο update(Change.NextPageLoading) μεσολαβεί ένα dispatch στο main looper. Δύο LoadNextPage που φτάνουν μέσα στο ίδιο frame περνούν και οι δύο τον φρουρό και εκκινούν δύο ταυτόχρονες κλήσεις για την ίδια σελίδα. Ο reducer κάνει dedup στα items, οπότε δεν βλέπει ο χρήστης διπλά, αλλά γίνεται περιττό network call και το loadJob χάνει την αναφορά στο ένα από τα δύο jobs (διαρροή: δεν μπορεί πια να ακυρωθεί).

Πρόταση. Ενημερώστε το state σύγχρονα, πριν το launch, και δώστε στο loadNextPage δικό του job reference:

private var appendJob: Job? = null

private fun loadNextPage() {
    val current = _state.value
    if (current.isLoading || current.isLoadingMore || current.endReached) return
    if (current.items.isEmpty()) return
    update(Change.NextPageLoading)          // σύγχρονα: ο φρουρός κλείνει αμέσως
    appendJob = viewModelScope.launch { load(page = current.page + 1, replace = false) }
}

Στην πλευρά του UI, ο τρόπος που προτείνει η Google είναι ένα snapshotFlow πάνω στο LazyListState, έξω από το item scope — αποσυνδέει το pagination από τη σύνθεση των γραμμών και δεν εξαρτάται από το ποιο item τυχαίνει να είναι στη σύνθεση:

val listState = rememberLazyListState()
LaunchedEffect(listState) {
    snapshotFlow {
        listState.layoutInfo.visibleItemsInfo.lastOrNull()?.index ?: 0
    }
        .distinctUntilChanged()
        .collect { lastVisible ->
            if (lastVisible >= state.items.lastIndex - PREFETCH_DISTANCE && state.canLoadMore) {
                onIntent(Intent.LoadNextPage)
            }
        }
}

Μεσαία M-5 Απεριόριστο fan-out στο refresh() των favorites

data/repository/FavoritesRepositoryImpl.kt:63-69

Το πρόβλημα. Το refresh() ξεκινά ένα async ανά αποθηκευμένο favorite, χωρίς όριο ταυτοχρονισμού. Το σχόλιο εξηγεί σωστά γιατί είναι παράλληλο («μια ντουζίνα favorites δεν πρέπει να σημαίνει μια ντουζίνα διαδοχικά round trips»), αλλά δεν βάζει ταβάνι.

Γιατί έχει σημασία. Τα favorites δεν έχουν ανώτατο όριο. Ένας χρήστης με 200 αποθηκευμένες ταινίες προκαλεί 200 ταυτόχρονα HTTP requests κάθε φορά που ανοίγει την καρτέλα Favorites — πάνω από το maxRequests (64) του OkHttp dispatcher, με μεγάλη πιθανότητα rate limiting από το TMDB και έντονη κατανάλωση μπαταρίας/δεδομένων. Το FavoritesRoute καλεί Refresh σε κάθε είσοδο στην οθόνη.

// Όριο ταυτοχρονισμού με Semaphore — κρατά την παραλληλία, βάζει ταβάνι
private val refreshLimit = Semaphore(MAX_PARALLEL_REFRESH)   // π.χ. 6

val refreshed = current.map { favorite ->
    async {
        refreshLimit.withPermit {
            movieRepository.movieDetails(favorite.id)
                .map { it.toMovie().toFavorite(favorite.addedAtEpochMillis) }
                .getOrDefault(favorite)
        }
    }
}.awaitAll()

Αξίζει επίσης ένας έλεγχος «πότε έγινε τελευταία φορά»: ένα refresh ανά είσοδο στην οθόνη είναι υπερβολικό όταν η μόνη αλλαγή που μπορεί να συμβεί είναι η γλώσσα. Ένα πεδίο lastRefreshedLanguage θα το περιόριζε σε μία φορά ανά πραγματική αλλαγή.

Μεσαία M-6 Το FavoritesViewModel αγνοεί το αποτέλεσμα του toggle

ui/favorites/FavoritesViewModel.kt:46-49

Μεσαία M-7 Ακύρωση κατά την ανάγνωση μπορεί να θεωρηθεί «καταστροφή αρχείου»

data/local/favorites/EncryptedFavoritesSerializer.kt:26-29

Το πρόβλημα. Το readFrom μετατρέπει κάθε Exception σε CorruptionException:

} catch (e: Exception) {
    throw CorruptionException("Favorites could not be read", e)   // και το CancellationException
}

Γιατί έχει σημασία. Το CorruptionException ενεργοποιεί τον ReplaceFileCorruptionHandler, που αντικαθιστά το αρχείο με κενό. Δηλαδή το «ο χρήστης χάνει τα αγαπημένα του» είναι η συνέπεια. Σήμερα ο κίνδυνος είναι θεωρητικός — μέσα στο try δεν υπάρχει suspension point, άρα δεν μπορεί ρεαλιστικά να πεταχτεί CancellationException εκεί. Είναι όμως ένα σημείο όπου μια μελλοντική αλλαγή (π.χ. μετακίνηση της αποκρυπτογράφησης σε withContext(Dispatchers.IO)) μετατρέπει αθόρυβα μια ακύρωση σε απώλεια δεδομένων.

Πρόταση. Ξεχωρίστε ρητά την ακύρωση — και περιορίστε το catch σε ό,τι πραγματικά σημαίνει κατεστραμμένο αρχείο:

return try {
    json.decodeFromString(FavoritesData.serializer(), crypto.decrypt(bytes).decodeToString())
} catch (e: CancellationException) {
    throw e                                                       // ακύρωση, όχι καταστροφή
} catch (e: CryptoUnavailableException) {
    throw CorruptionException("Favorites could not be decrypted", e)
} catch (e: SerializationException) {
    throw CorruptionException("Favorites payload is malformed", e)
}

Το ίδιο ισχύει και για το KeystoreCryptoManager.decrypt (γραμμή 59), όπου το catch (e: Exception) τυλίγει τα πάντα σε CryptoUnavailableException.

3. Ευρήματα χαμηλής προτεραιότητας

Χαμηλή L-1 Το ObserveEffects κρατάει stale lambda

ui/EffectCollector.kt:15-21

Το onEffect δεν είναι key του LaunchedEffect και δεν τυλίγεται σε rememberUpdatedState. Αν το lambda που περνιέται αλλάξει (π.χ. επειδή αλλάζει το navController ή κάποιο captured callback), η συλλογή θα συνεχίσει να καλεί το παλιό. Πρακτικά σπάνιο εδώ, αλλά είναι το καθιερωμένο pattern:

@Composable
fun <T> ObserveEffects(effects: Flow<T>, onEffect: (T) -> Unit) {
    val lifecycleOwner = LocalLifecycleOwner.current
    val currentOnEffect by rememberUpdatedState(onEffect)      // πάντα το τελευταίο
    LaunchedEffect(effects, lifecycleOwner) {
        lifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED) {
            effects.collect { currentOnEffect(it) }
        }
    }
}

Χαμηλή L-2 Δύο ίδια διαδοχικά μηνύματα: το δεύτερο χάνεται

ui/components/SnackbarMessage.kt:24-30

Το LaunchedEffect έχει key το ίδιο το κείμενο. Το onShown() καλείται μόνο αφού κλείσει το snackbar (το showSnackbar είναι suspend μέχρι το dismiss, ~4 δευτερόλεπτα). Αν στο διάστημα αυτό φτάσει δεύτερο μήνυμα με πανομοιότυπο κείμενο, το key δεν αλλάζει, το effect δεν ξανατρέχει, και το onShown() που ακολουθεί το μηδενίζει — το δεύτερο γεγονός εξαφανίζεται. Αυτό είναι το κλασικό πρόβλημα «one-off event μοντελοποιημένο ως state». Η καθιερωμένη λύση είναι να φέρει το γεγονός δική του ταυτότητα:

data class SnackbarEvent(val text: UiText, val id: Long = System.nanoTime())
// ...και το LaunchedEffect να κλειδώνει στο event.id αντί για το κείμενο.

Χαμηλή L-3 Ασυγχρόνιστη δημιουργία κλειδιού στο Keystore

data/local/crypto/KeystoreCryptoManager.kt:64-65

Το secretKey() κάνει «αν δεν υπάρχει, δημιούργησε» χωρίς κλείδωμα. Δύο ταυτόχρονοι καλούντες στην πρώτη χρήση μπορούν να δημιουργήσουν διαδοχικά δύο κλειδιά με το ίδιο alias· το δεύτερο αντικαθιστά το πρώτο, και ό,τι κρυπτογραφήθηκε με το πρώτο γίνεται μη αναγνώσιμο. Το DataStore σειριοποιεί σήμερα τα writes, οπότε το παράθυρο είναι πολύ στενό, αλλά ένα @Synchronized στο secretKey() το κλείνει με μηδενικό κόστος. Παράλληλα, το secretKey() κάνει lookup στο keystore σε κάθε encrypt/decrypt — μια by lazy τιμή θα ήταν αισθητά φθηνότερη.

5. Τι είναι ήδη σωστό

Καταγράφεται ρητά, γιατί αυτά είναι αποφάσεις που δεν πρέπει να «διορθωθούν» κατά λάθος σε επόμενο refactor.

  • Κατεύθυνση εξαρτήσεων. Τα repository interfaces ζουν στο domain/ και υλοποιούνται στο data/· οι mappers DTO → Domain είναι στο data layer, εκεί ακριβώς που ανήκουν. Το presentation δεν γνωρίζει ούτε Retrofit ούτε DataStore.
  • Τα σφάλματα είναι τύποι, όχι exceptions. Το AppError ως sealed interface, με το safeApiCall ως το μοναδικό σύνορο όπου σταματούν τα exceptions, είναι ακριβώς το σωστό μοτίβο — και το UiText κρατάει το Context έξω από τα ViewModels.
  • Το flag «αγαπημένο» δεν είναι μέρος του μοντέλου του TMDB. Τα favorite ids έρχονται ως ξεχωριστό Flow και ο reducer ξαναμαρκάρει τις ήδη ορατές γραμμές. Έτσι το favoriting δεν προκαλεί επαναφόρτωση και η λίστα είναι ήδη σωστή κατά την επιστροφή από τις λεπτομέρειες. Αυτό είναι δύσκολο να γίνει σωστά και έχει γίνει σωστά.
  • Κρυπτογράφηση. AES-256/GCM με setRandomizedEncryptionRequired(true), versioned payload ([version][IV][ciphertext‖tag]), κλειδί που δεν φεύγει ποτέ από το Keystore, χειρισμός του KeyPermanentlyInvalidatedException, allowBackup=false με ρητούς κανόνες εξαγωγής. Και, το σημαντικότερο, ειλικρινές threat model στο README που λέει τι δεν προστατεύει.
  • Το test που αποδεικνύει την κρυπτογράφηση. Το the_stored_file_never_holds_the_title_in_clear_text διαβάζει το αρχείο ως bytes και ελέγχει ότι ο τίτλος δεν είναι μέσα. Ένα assertion που αποδεικνύει το ουσιώδες, αντί για δέκα που αποδεικνύουν το προφανές.
  • Type-safe navigation. @Serializable destinations χωρίς χτίσιμο route strings, με το movieId να διαβάζεται από το SavedStateHandle — ο σύγχρονος τρόπος του Navigation Compose.
  • Η αιτιολόγηση των αποφάσεων. Το README εξηγεί γιατί δεν χρησιμοποιείται Paging 3, γιατί δεν υπάρχει BaseMviViewModel, γιατί δεν χρησιμοποιείται EncryptedSharedPreferences. Το να τεκμηριώνεις τι απέρριψες και γιατί είναι πιο χρήσιμο από το να τεκμηριώνεις τι έκανες.
  • Τα σχόλια στον κώδικα εξηγούν το «γιατί». Η σειρά των modifiers στο widthIn/fillMaxWidth, η επιλογή του SystemBarStyle ανά night mode, ο λόγος που ο LanguageInterceptor μπαίνει πριν από τον logger. Αυτά είναι σχόλια που γλιτώνουν πραγματικό χρόνο.
  • Υποδομή μετρήσεων ήδη στημένη. Τα composeCompiler.metricsDestination/reportsDestination είναι ρυθμισμένα — δηλαδή το εργαλείο για να επαληθευτεί το M-2 υπάρχει ήδη και χρειάζεται μόνο να διαβαστεί μετά το build.
